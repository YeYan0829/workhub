# 首次体验与模型接入

这份指南帮助你从一个空环境开始，体验 README 中的报表发布场景，再按需开启项目助手和语义检索。

## 先选择体验范围

| 想体验什么 | 需要准备什么 | 完成后可以做什么 |
|---|---|---|
| 任务与多人协作 | Docker Compose v2、Python 3；源码构建还需 BuildKit | 注册、建团队、建项目、管理依赖与资料、查看实时更新 |
| 项目助手 | 基础环境、团队文本模型密钥、部署加密主密钥、专用 Redis | 问项目进展、查直接阻塞、核对回答引用、辅助分诊 |
| 项目资料关键词检索 | 基础环境与 Elasticsearch | 检索文档、任务及讨论正文 |
| 语义与混合检索 | Elasticsearch、团队 Embedding 连接、专用 Redis、项目索引准备 | 用语义查资料，结合关键词和向量结果 |
| GitHub Issue 同步 | GitHub App、安装与仓库授权 | 把仓库反馈同步为项目任务，并按需回写 |

基础环境使用 WorkHub、MySQL、RabbitMQ 和 Mailpit 四个容器，声明的内存上限合计 2GiB。Elasticsearch 与模型专用 Redis 的上限合计再增加 1,152MiB；Docker 与操作系统还需自己的内存空间。

## 启动基础环境

### 从源码构建

下载并解压仓库源码，或克隆仓库，进入包含 `compose.yaml` 的目录：

```bash
python3 scripts/init-env.py
docker compose --profile app up --build -d --wait --wait-timeout 300
```

初始化脚本创建本地 `.env`，生成数据库与消息服务密码；已有 `.env` 会保留。首次构建需要下载 Java 构建镜像、依赖和中间件镜像，后续构建可复用缓存。

成功启动后打开：

- 应用：<http://127.0.0.1:18080>
- 测试邮箱：<http://127.0.0.1:18025>

### 使用已构建的应用镜像

从 [v0.1.0-preview.2 版本页](https://github.com/YeYan0829/workhub/releases/tag/v0.1.0-preview.2)下载应用镜像、同版本源码包和校验清单，按[预览版安装](RELEASE.md)加载镜像并启动。该版本提供 `linux/amd64` 镜像。

拿到镜像后，使用同版本源码包中的 Compose、初始化脚本和配置模板启动。两种镜像交付形式的准备步骤如下：

| 镜像形式 | 准备步骤 |
|---|---|
| 镜像仓库地址 | 按版本发布页给出的完整引用执行 `docker pull`，将同一引用写入 `.env` 的 `WORKHUB_IMAGE` |
| 离线镜像包 | 按发布页校验 SHA-256，再执行 `docker load -i 镜像包文件`，将输出的镜像标签写入 `.env` 的 `WORKHUB_IMAGE` |

例如，加载预览版镜像后执行：

```bash
python3 scripts/init-env.py --image workhub:v0.1.0-preview.2
```

然后启动整个应用环境，复用这份镜像：

```bash
docker compose --profile app up --no-build -d --wait --wait-timeout 300
```

`--no-build` 让 Compose 直接使用选定镜像。MySQL、RabbitMQ 和 Mailpit 仍是配套服务，首次使用时 Docker 会获取它们各自的镜像。离线部署需要同时准备这些依赖镜像。

## 建立第一个团队和项目

1. 在应用首页选择注册，填写登录名、显示名、演示邮箱和至少 12 位密码。
2. 打开 Mailpit，找到该邮箱的验证邮件，点击链接并确认验证。Mailpit 接收本地测试邮件，演示邮箱可以使用 `alice@example.test`。
3. 回到应用登录，进入“团队与项目”，创建“星河产品团队”。
4. 在团队中创建“客户报表发布”项目。创建者拥有维护该项目的权限。
5. 打开“项目任务”，展开创建任务表单。初次单人体验时，可将负责人都选为自己，初始状态选待办。

## 按报表发布场景走一遍

### 创建工作与依赖

先创建以下任务。表内字母只是说明依赖的代号，填写标题时使用实际任务名。

| 代号 | 标题 | 创建后调整的状态 | 在该任务的“依赖”中添加的上游 |
|---|---|---|---|
| A | 确定报表字段与接口 | 完成 | 无 |
| B | 完成报表页面与导出入口 | 完成 | A |
| C | 修复筛选后导出遗漏数据 | 待办 | 无 |
| D | 回归筛选与导出结果 | 待办 | B、C |
| E | 补齐报表使用说明 | 进行中 | 无 |
| F | 完成报表发布验收 | 待办 | D、E |
| G | 发布报表功能公告 | 待办 | F |
| H | 整理功能截图素材 | 待办 | 无 |

进入一个任务，选择“编辑任务”调整状态。在“依赖”里展开“添加上游任务”，输入标题并从建议中选择，再保存。例如在 D 中添加 C，表示先修复导出遗漏，再开展回归。

进入“项目文档”，创建“报表发布验收清单”，正文可写：

> 导出数据应与筛选页面一致；回归通过、使用说明补齐后，再确认发布验收。截图素材可并行整理。

回到 F 的“文档与链接”关联这份资料，并在评论中补充“回归覆盖日期筛选、跨页导出和导出行数”。

### 看清当前阻塞

打开“项目概览”，应当能够看到：

- D 等待 C 完成；B 已经完成。
- F 同时等待 D 与 E；G 等待 F。
- H 可以独立推进。

选择 F，查看它的上下游、负责人和最近讨论；从侧栏继续打开完整任务或文档。项目较大时，使用搜索定位任务，再展开直接上下游。

这套依赖用于帮助判断工作安排。上游未完成时页面会提示阻塞，成员仍可依据实际情况处理任务状态。

### 体验实时更新

保留一个浏览器窗口显示概览，再打开另一个标签页，把 C 改为完成。回到概览，观察 D 的直接阻塞解除，而 F 继续等待回归和说明。

想体验不同成员协作，可以用另一个浏览器配置文件注册第二个账号。管理员在团队“成员与邀请”中邀请该账号，成员从邮件接受邀请后，维护者再在“项目管理”授予项目成员权限。将 C 分配给第二个成员，再重复上述操作。

团队成员身份和项目访问权分别管理：先加入团队，再进入获授权的项目。

## 开启项目助手

### 1. 部署者准备模型环境

保留当前 `.env`，增加或更新：

```dotenv
WORKHUB_AGENT_ENABLED=true
WORKHUB_MODEL_ADMISSION_ENABLED=true
WORKHUB_MODEL_MASTER_KEY=填写生成的32字节Base64主密钥
```

可以用以下命令生成主密钥，将输出保存到 `.env` 对应字段：

```bash
python3 -c "import base64,secrets; print(base64.b64encode(secrets.token_bytes(32)).decode())"
```

这个主密钥用于加密团队配置的供应商密钥。后续启动沿用它，与数据库一起备份。

从源码启动模型环境：

```bash
docker compose --profile app --profile model-governance up --build -d --wait --wait-timeout 300
```

使用已有镜像时，将上述 `--build` 换为 `--no-build`。

### 2. 团队管理员配置文本模型

在团队页进入“模型服务”，选择界面目录中的供应商与模型，填写自己的 API key、调用速率和突发容量，启用后保存。项目成员使用团队连接，项目维护者决定本项目的模型与分析限制。

第一次配置还需要部署者初始化这份连接的共享配额状态。根据当前连接的 `quotaScope`、`version`、`requestsPerSecond`、`burst` 填写初始化参数；读取接口与操作说明见[Redis 初始化和恢复](ARCHITECTURE.md#redis-初始化和恢复)。

例如连接版本为 1、每秒 4 次、突发容量 2 时，使用真实团队 UUID 替换下列示例：

```bash
python3 scripts/model-admission.py initialize --scope 'team-<workspace-uuid>' \
  --team-version 1 --rate 4 --burst 2 --port 16380 \
  --recovery-ms 1000 --confirmed-prior-cooldown
```

其中 `<workspace-uuid>` 是占位符，填写后再执行。示例的 1000ms 用于没有先前冷却的首次初始化；已有供应商冷却时，恢复等待还要覆盖其剩余时间，再确认执行初始化。

### 3. 提问、继续追问，并核对原文

进入项目“模型与检索”，选择继承团队默认模型或指定模型，设置单次分析的请求次数与最长执行时间。

打开“询问助手”或项目助手侧栏，围绕刚才的场景提问：

> 报表发布目前卡在哪里？请列出直接阻塞、相关负责人和依据，说明哪些工作可以并行。

阅读时核对任务状态与当前项目是否一致：如果之前已经将 C 改为完成，D 的直接阻塞已经解除，而 F 仍等待 D 与 E。引用中的任务记录帮助核对当前状态，验收清单解释完成条件。

为了体验正文问答，在“项目文档”中再创建“筛选导出回归步骤”，正文可写：

> 准备至少两页数据，按客户和日期筛选，比较页面结果与导出文件的行数、字段，并记录跨页导出的验证结果。

将它关联到 C 和 D。在同一助手会话中继续问：

> 回归前需要准备什么，具体核对哪些结果？请引用项目中的回归步骤。

点击回答中的引用编号，查看对应的来源卡片。“当前阻塞”列出等待的任务，“任务信息”显示负责人、状态与优先级，“任务描述”和“文档原文”展示实际片段。打开文档原文，核对“至少两页数据”、筛选条件与行数比较是否对应正文。返回会话后可以继续追问。任务页的“询问助手”会预填任务标题和 ID，方便围绕具体工作提问。

助手通过项目内工具读取任务和关系，也能使用已准备的资料检索。首次可先体验任务事实查询，再启用下面的全文与向量检索。

### 4. 新反馈自动分析，再由维护者核对

先由维护者进入“项目管理”，找到“新任务自动分析”，设置为开启，选择默认分析方式并保存。例如“固定资料并补充查证”会先收集资料，再允许模型进行有限的补充查询。

随后提交一条状态为待分诊的新任务，标题使用“导出时支持自定义列顺序”，描述可写：

> 希望导出的客户、日期、金额列能调整顺序，便于粘贴到财务模板。

系统会自动排队分析。维护者打开该任务的“分诊与接纳”，查看自动分析记录，等待结果，核对建议类型、优先级、相关任务、依据和待补问题。首次体验直接使用原始反馈，观察助手如何区分这项需求与现有的导出遗漏修复。

分析可能建议接纳、先补充资料或核对疑似重复项。缺少影响范围或项目优先级约定时，优先级可以留空；待补问题供后续沟通使用。

确认接纳时，按实际安排编辑类型、优先级，选择负责人并填写调整说明，点击“保存为新版本”，再点击“校验并预览此版本”，核对后明确批准。刷新任务，检查原任务已进入待办，负责人和优先级与批准内容一致。

需要补充资料时，先保留待分诊，补充描述或讨论，再通过“分析这项任务”重新调查。普通助手会话用于连续问答；分诊区的分析记录和接纳提案在当前任务内查看。

已连接 GitHub 的项目可以用新 Issue 体验自动触发：先开启自动分诊，再在已授权仓库创建 Issue，等待首次同步。符合条件的新反馈会自动分析，历史回填资料用于同步。完整触发条件见[GitHub 集成](ARCHITECTURE.md#github-同步与远端意图)。

## 开启全文、语义与混合检索

先在 `.env` 设置 `WORKHUB_RETRIEVAL_ENABLED=true`。向量检索再设置 `WORKHUB_EMBEDDING_ENABLED=true`，并沿用前述主密钥与专用 Redis。启动附加依赖：

```bash
docker compose --profile app --profile retrieval --profile model-governance \
  up --build -d --wait --wait-timeout 300
```

团队管理员在“模型服务”配置 Embedding 连接。当前团队目录支持百炼北京地域的 `text-embedding-v4`；填写模型、维度、密钥和供应商业务空间 ID。WorkHub 团队 UUID 与百炼业务空间 ID 分别来自两个系统，按表单说明填写。

独立 Embedding 连接使用自己的配额域；显式复用百炼文本生成连接时沿用其有效域。部署者按连接返回的 `quota` 中 scope/version/rate/burst 初始化，详见[团队 Embedding 与索引切换](ARCHITECTURE.md#团队-embedding-与索引切换)。

项目维护者在“模型与检索”启用目标空间，发起重建，等待目标资料覆盖就绪，再切换为当前使用空间。准备期间可以继续维护项目内容；切换后，在资料搜索中比较关键词、语义和混合结果，并打开原文核对。

## 连接 GitHub

GitHub 集成由部署者创建和配置 GitHub App，挂载私钥，为团队预授权安装与仓库；维护者再从项目“GitHub 来源”连接仓库、同步 Issue。需要回写时开启远端写回，并通过页面跟踪处理状态。

GitHub 的集成机制与部署预授权命令见[架构与运行说明](ARCHITECTURE.md)。首次接入还需完成 GitHub App 外部配置，以及容器中私钥文件的挂载与读取权限设置；这部分由部署者按自己的仓库环境准备。基础协作和模型接入可以分别完成，再接入真实仓库。

## 更新、停止与常见问题

| 遇到什么情况 | 如何处理 |
|---|---|
| 注册后找不到邮件 | 打开 Mailpit，按收件邮箱查找；查看应用与 RabbitMQ 日志 |
| 验证邮件跳到错误地址 | 将 `.env` 的 `WORKHUB_PUBLIC_URL` 改为浏览器实际使用地址，重新创建应用容器并申请新邮件 |
| 加入团队后看不到项目 | 请维护者在“项目管理”授予项目访问权 |
| 助手显示尚未配置或暂停 | 依次检查部署开关、团队连接、配额域初始化、项目模型策略 |
| 语义检索仍在准备 | 查看目标空间的覆盖和失败任务，待就绪后确认切换 |
| Docker 提示镜像不存在 | 核对 `WORKHUB_IMAGE` 与拉取/加载的实际标签；源码路线使用 `--build` |
| 需要查看日志 | `docker compose --profile app logs -f app` |
| 停止基础环境并保留数据 | `docker compose --profile app down` |

启用附加 profile 后，停止环境时沿用同一组 profile，例如 `docker compose --profile app --profile retrieval --profile model-governance down`。

更新源码后重新构建；使用发布镜像时，先备份数据库与密钥，再按该版本说明更新镜像引用并重新创建应用。业务数据库、邮件密钥卷和部署模型主密钥共同构成恢复所需资料。详细验证流程见[测试说明](TESTING.md)，已测结果见[实验报告](VALIDATION.md)。
