# 产品与业务行为

公开基线 · 2026-11-04。WorkHub 支持团队与项目授权、任务及依赖、文档、CSV 导入和预授权 GitHub 仓库同步。项目知识支持正文与向量检索；只读助手和分诊建议由部署配置显式开启。运行方式与验证范围见[根 README](../README.md)。

## Project Agent（5A 最小切片）

项目内的 Project Agent 入口接受自然语言问题，后台读取绑定项目的当前任务、阻塞与依赖、关联资料、同步状态及知识证据。身份、项目、授权和预算由服务器决定。当前事实以业务数据库为准；页面用服务端结构化字段展示状态、优先级与负责人，文本证据、推断和未知内容分开展示，并提供来源与观察时间。点击来源进入现有 Task、Document 或 GitHub 对象；历史评论在关联 Task 内核对。

读取每次运行时重新检查当前权限、项目版本及所用来源，撤权不返回答案；上下文失效要求重新提问。证据不足、降级、限流、超时和非法回答显示明确限制或失败。当前只允许读工具，业务 Task/DAG 不因提问而修改；仅持久化运行、审计和后台义务。5B 已增加下述单任务分诊流程。5A 最小只读基线已收尾：已有真实 GLM 自主工具选择、回答与定向回归证据，但完整业务 Benchmark 和广泛稳定性仍未验收。普通问答继续只读；分诊建议通过单独入口，经维护者预览并明确批准后由 Java 执行。

### 分诊调查与能力范围

维护者可选择固定资料分析、固定资料并补充查证、自主调查，并填写可选关注点。三种策略均只读，输出字段建议、相关或疑似重复任务的理由与引用，以及待补充问题；疑似重复不会自动合并或建立关系。资料不足是业务结果，不等于执行失败。

自动分诊已支持项目级显式开关，默认关闭，触发与停止规则见下文。聊天协助创建任务尚未实现，普通聊天只读；不代发评论、不创建文档、不执行 GitHub 远端写回。模型实际调用仍需独立配置和预算授权，开启项目自动分诊不等于获得付费授权。

### 单任务 Agent 分诊（5B）

维护者在已有本地待分诊任务详情中点击“分析这项任务”，查看带来源的类型/优先级建议。资料不足时字段可留空；分析、保存、编辑和预览均不修改任务。负责人由维护者从有效项目成员中选择，不根据角色名推断技能或工作量。截止日期默认保留任务原值，维护者可按已有接纳合同编辑或清空，不引入新的日期规则。

分诊分析归属项目与目标任务，原发起者仅保留为审计信息。维护者降权、移出项目或账号停用不取消已登记的项目分析；当前有效维护者可通过任务的分析历史接口找到Run、读取结果并转为提案。普通成员不具备该维护入口，个人问答仍只供本人访问。新维护者接续已有提案必须使用自己的新预览凭据批准，不能复用前任的批准令牌。后端接续接口已提供，任务页面可从运行历史发现已有分析，运行历史与提案历史分开展示。

项目归档后，尚未消费的分诊不会调用模型；运行中在后续调用准入边界停止。目标任务撤回、拒绝、已接纳或不存在时也停止无效调查。调用预留与归档/任务修改按项目锁确定先后，锁在模型网络请求前释放；已获准进入调用的请求可能仍产生实际或未知费用，归档不退款、不清除账本。保留既有Run终态与错误码，不另建任务状态机；任务硬删除目前没有产品入口。

提案历史按初版创建时间和ID稳定排序，编辑旧版本不会将其变成最新分析。现有页面接口返回最近30条、按时间升序排列，以便继续默认选择最后一条；新增历史接口按时间降序分页，供后续前端浏览更早结果。

“保存为新版本”后须点击“校验并预览此版本”，核对修改前后字段，再点击“明确批准版本 N 并接纳”。未保存的编辑会移除旧批准入口。批准仅针对这一任务，将已确认的类型、优先级、负责人、日期与 TODO 状态原子提交。旧版本或过期资料不能接纳，重新分析后再决定；执行失败显示错误并保留提案，成功显示实际结果，刷新任务页可重开已存收据。成功结果以执行当时快照展示；后续任务变化不改写历史收据。撤权者不能继续查看或批准。

首版不支持批量分诊、任意修改、评论/文档创建或 GitHub 写回。仓库保留合成夹具和本地模型替身的工程验证；相关测试见 [TriageProposalIT](../src/test/java/dev/workhub/phase5b/TriageProposalIT.java) 与 [AutomaticTriageIT](../src/test/java/dev/workhub/phase5b/AutomaticTriageIT.java)。这些测试不代表真实模型回答质量。

## 导航与信息范围（2026-09-27 交互修订）

固定个人入口为“我的任务 / 通知 / 团队与项目”；团队导航是进入某个团队的入口，不隐式改变个人总览的范围。团队内部再分项目、成员与邀请、设置与交接；项目内部显示任务、文档、导入、GitHub 和项目管理。详情面包屑始终显示团队 → 项目 → 当前内容。

“我的任务”默认跨全部团队，限当前账号负责且仍有项目访问权的任务，包括已完成任务和归档项目；创建或订阅不等于负责。每行显示所属团队与项目，支持服务端团队/项目/状态/标题筛选与分页。筛选保存在 URL，打开详情再返回可恢复列表。项目选择器最多列出1000个可访问项目。

“通知”是站内全局入口，汇总现有项目通知，提供全局未读数、团队/项目/未读筛选、游标分页、标读与任务跳转。团队邀请通过邮件送达，已验证收件人也可在“团队与项目”查看并接受待处理邀请；它不计入任务通知的未读数。项目页“查看本项目通知”进入同一个通知中心并带项目筛选，旧项目通知地址也转到这里。未读数、列表与标读使用相同的当前授权范围；撤权后的通知不继续出现在全局入口，其他团队合法内容保留。

设计参考官方文档：[Linear My Issues](https://linear.app/docs/my-issues)、[Linear Inbox](https://linear.app/docs/inbox)、[Workspace 切换](https://linear.app/docs/workspaces)、[Asana Inbox](https://asana.com/features/project-management/inbox)。借鉴的是固定个人入口、可辨认的空间上下文、通知关联具体工作以及将管理入口分开。Linear Inbox 明确以 Workspace 为范围；本项目保留原有跨 Workspace 个人聚合，并用显式范围和来源列解释，不将两者混为同一产品规则。没有引入成熟产品的全部功能或额外前端框架。

## 账号与团队

同一浏览器配置通过 Cookie 共享一个当前登录会话；切换账号影响该配置下的其他标签页。多账号同时体验需使用独立浏览器配置或普通窗口与无痕窗口。

注册用户名使用 3–60 位 ASCII 字母、数字、下划线、短横线；密码至少12字符、UTF-8不超过72字节，BCrypt 存储。邮箱归一化并唯一；新账号验证后启用。已有身份、署名与作者外键保留，旧账号可在个人资料中用当前密码绑定邮箱。改密/重置失效全部 JDBC sessions。登录、注册、邮件请求等有限频；验证24小时、重置30分钟，凭证摘要存储、一次性消费，邮件正文加密持久化，成功 SMTP 投递后清除链接正文。SMTP 成功不等于用户收到；跨 SMTP 故障可能重复邮件，不承诺 exactly-once。

Workspace ADMIN 管团队，MEMBER 可创建项目，创建者成为 Project MAINTAINER。加入空间不加入全部项目；ADMIN 不自动读项目正文。访问项目需要用户、空间成员、项目成员均有效。

邀请7天有效，允许邀请尚未注册的邮箱，仅授予空间 MEMBER，邮件与已验证当前账号匹配才可接受。持有邀请链接可查看收件邮箱、团队名称、邀请状态与注册/验证引导；不提供按任意邮箱查询用户的入口。未注册者先注册并验证，已注册者登录；错误账号先明确提示切换，不显示接受按钮。注册及重发验证邮件可携带与邮箱匹配的有效邀请，邮件链接保留上下文，验证和登录后继续原邀请，仍需用户明确接受。已接受、撤回、过期或无效链接显示对应结果。 “团队与项目”同时显示当前账号、待接受邀请和已加入团队。待接受列表只查询当前有效账号的已验证邮箱，排除已接受、撤回和过期记录；应用内按邀请 ID 接受与邮件 token 接受使用同一事务校验，不能凭 ID 加入其他邮箱的团队。重复打开已验证邮箱的邮件可返回原邀请，验证本身不会创建团队成员。有效同邮箱邀请复用原邀请，撤销/过期后需重发；重复接受不重复授权，已接受邀请不能用于撤权后重新加入。离开/移除时旧项目成员关系停用并清除旧角色；重新邀请后仍需明确加入项目。其他 Workspace 的合法访问不受影响。

并发退出/降权/移除不能移走最后 ADMIN 或最后 MAINTAINER，包括归档项目。ADMIN 的管理摘要只展示项目名称/状态；显式维护者交接授予所选成员项目维护权并记录管理事实，随后才能移除原成员。普通项目成员只能由 MAINTAINER 增删/改角色。历史任务、署名与已完成结果保留；失效成员不可新分配，任务列表可筛选“负责人已失效”后改派。

## 项目与日常任务

项目支持详情、成员管理、归档与恢复；归档项目可读，拒绝人工业务写入、新导入与新 GitHub 发送。维护者仍可恢复项目，ADMIN 可执行必要交接。后台每行/分页提交重查授权与归档；归档不能撤销已发送的远端请求，既有未知请求继续只读观察确认。

任务有 title/description、TRIAGE/TODO/IN_PROGRESS/DONE/CANCELED、TASK/BUG/FEATURE/QUESTION、0–3 优先级、可空日期。普通项目成员创建任务默认 TRIAGE，不能通过请求指定 TODO、正式优先级或负责人。维护者可直接创建待办，也可提交待分诊任务。待分诊创建者可完善标题、描述、日期、上游依赖及关联资料，或撤回申请；不能决定正式指派、优先级、类型或推进执行状态。维护者接纳接口要求有效负责人，将负责人、优先级、日期等安排与 TODO 状态在同一对象版本检查和事务内提交。

GitHub 同步形成的待分诊任务也支持维护者手动发起 AI 分析、核对引用、编辑提案并预览批准；后台沿用项目范围只读分析权限，普通成员不能发起或批准分诊建议。批准只接纳 WorkHub 中的任务，不发送 GitHub 修改请求。远端正文、关闭状态或已引用资料改变时，旧提案仍须通过版本与来源校验。对应工程验证见 [GitHubTriageIT](../src/test/java/dev/workhub/phase5b/GitHubTriageIT.java)，使用本地 GitHub HTTP 替身和脚本模型。自动分析默认关闭。维护者开启后，新建本地待分诊任务及符合条件的 GitHub 首次镜像可自动登记一次分析：GitHub 创建时间必须可信且晚于本次开启时间，首次发现须来自 opened 通知或增量补扫，并仍待分诊。首次历史回填、创建时间缺失/异常、旧问题及因编辑/重开才首次发现的问题保留人工入口；已有任务的编辑、评论与重开不自动重跑。开启者离任不撤销项目的只读分析授权；审计记录保留授权设置版本、开启者及触发资源/Job。关闭会结束排队中的自动 Run，并为运行中的自动 Run 留下不可因重新开启而清除的停止标记；已发模型请求继续结算，手动分析不受影响。首次排队超过600秒，在下一次 worker 检查时明确失败；消息系统不可用期间不承诺即时更新终态。当前实现见 [AutomaticTriage](../src/main/java/dev/workhub/agent/AutomaticTriage.java)，验证见 [AutomaticTriageIT](../src/test/java/dev/workhub/phase5b/AutomaticTriageIT.java)。

接纳后，创建者身份不再赋予编辑权；当前负责人可修改描述、在 TODO/IN_PROGRESS/DONE 间推进或重开、维护自身上游依赖和关联资料。正式标题、类型、截止日期、优先级、指派由维护者管理，正式取消、拒绝、退回分诊及接纳也由维护者执行。未指派的已接纳历史任务由维护者维护。创建者同时被指派时按负责人身份编辑；改派后旧负责人立即失权，新负责人获得权限。其他成员继续查看、评论。撤回或拒绝以 CANCELED 保留申请，不能自行恢复；维护者可恢复到 TRIAGE，再接纳。triageRequired 不因撤回而清除，避免跳过接纳。旧待办/进行中/已完成任务按已接纳处理，不改写既有工作结果。

任务详情默认阅读，先展示信息和描述，再展示上下游依赖与关联资料，评论位于最下方。待分诊任务的维护者在标题旁看到与“编辑任务”并列的“分诊与接纳”按钮。点击“编辑任务”才出现当前身份、阶段允许修改的字段；取消不写入，保存成功返回阅读，冲突保留草稿。详情能力字段与服务端提交鉴权使用同一规则，旧页面不能沿用过时权限。归档隐藏写入口并在服务端拒绝。GitHub 标题与正式取消仅维护者可请求；已接纳负责人可请求正文和执行状态变化。新 GitHub TRIAGE 镜像同样等待本地接纳；待分诊创建者仅能请求完善正文，不能通过远端状态请求提前推进任务，发送前再次检查阶段权限。远端确认仍按现有协议应用权威状态。

当前负责人可提交“更换负责人申请”，包含原因与 expectedTaskRevision，每个任务至多一份 PENDING。提交不改变当前指派或编辑权，通知当前有效维护者。维护者按申请 revision 和当前任务 revision 处理：批准需选择另一位有效项目成员，决定和改派同事务；拒绝保留原指派，可填写处理说明。申请保留 PENDING/APPROVED/REJECTED/SUPERSEDED 状态及处理人、原因、时间；独立改派、退回分诊或正式取消会使待处理申请失效。并发提交不会产生两份待处理申请，并发处理不会改派两次；归档、撤权、旧版本提交均被拦截。申请、决定与接纳结果进入站内通知，不引入邮件审批。

Task PATCH 必须提供 If-Match revision；文档和评论使用同样的对象版本检查。版本冲突返回409，页面提示刷新后重试，不盲目覆盖。项目成员可协作文档；评论仅作者可编辑，作者或维护者可管理删除，保留删除事实和历史作者。外部评论保留 GitHub 来源与外部 login，不映射本地身份。评论操作按钮按当前作者/项目角色显示；普通成员看不到他人的删除入口，维护者通过“评论与讨论”右上角“管理评论”进入管理模式，才显示删除按钮；作者自己的编辑与删除收在“我的评论操作”中。输入 @ 后可按显示名称或登录名筛选当前有效项目成员，使用鼠标或方向键、Enter 插入精确 @login。团队内未加入项目的成员不会成为此项目的提及候选。隐藏按钮不替代服务端鉴权，归档时隐藏这些写入口。

项目列表支持标题包含、状态分组、负责人/未分配/失效负责人、直接阻塞与截止日期；我的任务跨当前有权限的项目查询。新查询以 offset/limit 分页，limit 上限沿用 Inputs.limit，offset 上限100000；旧 keyset API 保留。大规模全文/语义检索仍留到后续阶段。详情聚合成员、直接依赖、文档/网页、内部/外部评论、最近活动与同步状态；聚合窗口有界，更多内容通过既有分页接口读取。

## 依赖、内容与通知

A → B 表示 A 阻塞 B；同项目 DAG，不允许自环/重复/成环。isBlocked 只考虑直接上游且其状态不是 DONE；CANCELED 仍阻塞。可在被阻塞时标为 DONE，此时 dependencyRisk=true。上游重开不会自动重开下游。解除直接阻塞产生 Activity 并通知当前有效负责人；即使操作者同时负责上游和下游也保留提醒，只有真实 blocked→unblocked 转换才产生这一事实。任务详情用“上游依赖”表示当前任务的前置工作，用“下游工作”表示依赖当前任务的其他任务；上下游为空分别解释含义。依赖 A → B 的新增、删除和内部批次替换均按被阻塞任务 B 的当前编辑权授权；对 A 的编辑权不能单独决定 B 等待 A。待分诊创建者、已接纳负责人或维护者展开一个“添加上游任务”入口，输入标题后在同一输入框下方显示建议列表，支持方向键与 Enter 选择、Esc 收起，明确选择结果再点击添加；无需先提交独立的查找表单。建立依赖只选择同项目任务，排除自身和已添加的直接上游；按标题查找，最多展示100项匹配并提示截断，成环仍由后端原子检查。没有候选时在建议位置显示没有匹配或尚无其他任务的原因，不显示空选择器。输入变化立即清除旧选择；异步结果按序列和当前焦点过滤，避免将旧搜索结果误添加。

文档独立属于项目，可关联任务。维护者可按当前文档版本软删除，保留历史外键和审计，删除后退出列表、详情和检索。网页只存 HTTP(S) 引用，不抓取正文。

## 项目知识检索（4A）

项目“知识检索”搜索 Task 标题/描述、文档及内部/外部评论；GitHub Issue 描述复用已同步 Task 正文，不把负责人、状态、依赖或权限当向量知识。BM25 返回当前正文片段、来源链接与版本/字符范围；实时业务状态仍以任务详情为准。PR/CI 元数据和任意网页正文不自动成为语料。

正文变更同事务登记来源和后台索引义务。检索限当前有效项目成员，归档项目仍可读；ES 候选必须通过当前授权、owner 可见性、版本、hash 和 canonical 正文核验。更新、删除或撤权后的旧片段被过滤；索引落后/候选失效有提示，检索服务不可用明确返回503。

维护者可分批登记“回填 / 重建”，补齐存量来源并创建新的索引工作，覆盖早期 validation DONE、历史失败或 ES 索引丢失；202 只表示已受理，可刷新查看后台进度。历史 DONE 不被重开。资料数量与“已登记索引”是数据库逻辑状态，不代表 ES 物理健康检查。默认不开启检索，运行配置见根 README。

创建者、负责人、评论者和新评论 @login 提及者参与订阅；显式退订不被自动恢复。通知包括新负责人、新评论、解除阻塞、待分诊提交/接纳/拒绝、负责人交接申请与处理结果及已有 GitHub 错误。同一事实、同一收件人的多个通知原因合并，避免创建者兼任负责人时重复写入。普通通知过滤操作者，解除依赖通知保留当前负责人即使其是操作者；所有通知均过滤已无权限收件人，读取/标读重查权限。编辑评论不重新发送提及通知。Activity 保存选定业务事实；管理记录补充邀请、成员/角色、交接、项目及连接管理，不是全量事件存储。

项目 GitHub 页面包含接入配置向导：维护者可查看服务器是否已填写 App 配置、读取和写回开关、当前团队授权仓库数量，以及部署者提供的公开 App 安装链接；不返回私钥、路径、Token 或 webhook secret。配置填写不等于实时 GitHub 授权成功，实际读取以下方运行结果为准。安装和仓库访问由 GitHub 仓库拥有者授权，团队归属由部署者核验登记，维护者最后选择仓库连接。公开用户的 OAuth、安装回调和所有权自动绑定尚未实现。读取记录按开始时间展示每轮扫描，明确显示发现、已应用、失败、待处理数量；应用计数不等于新建任务数或任务完成数。

## CSV 导入

CSV 正式安排入口仅项目维护者可上传、确认和恢复，后台每行提交重查维护权，原上传者降权也不能继续。普通成员通过任务页提交待分诊申请。

UTF-8 固定表头 `title,description,type,priority,due_date,assignee_login`；1 MiB、1000行、单字段10000字符（标题500）、日期 ISO YYYY-MM-DD。类型与优先级须合法；负责人只精确匹配有效项目成员 login。无 Excel、通用映射或依赖图批量导入。

上传冻结输入与摘要，预检查逐行显示错误；确认后按行 WorkJob 提交，允许部分成功。稳定身份为导入 ID + 行号，任务、行结果和 WorkJob 完成同事务；重复确认、重复消费和进程恢复不会重建成功行。相同文件以新幂等键再次上传是**新的导入**，页面明确说明；技术恢复使用原导入，不重新上传。

状态为 PREVIEW/RUNNING/SUCCEEDED/PARTIAL_FAILED/FAILED/STOPPED。已成功、失败、未处理数量按实际行结果统计。撤权/归档停止后续写入；有效维护者可在恢复权限/项目后接手原导入，成功行保留，失败/未处理行重查。文件内容不可编辑，格式错误需新文件；无底层盲重试按钮。数据库终态执行失败也写入对应行结果。

源文件和报告继承项目权限，下载时重查；输入保留30天，过期拒绝下载/恢复，后台清除输入正文；任务及结果摘要保留。没有永久公开下载链接。

## GitHub

部署者配置预授权 GitHub App，不要求每个成员绑定 GitHub。installation 只归属一个 Workspace，repository 必须在正式部署命令配置的范围；连接者必须是 MAINTAINER。V6 已有无歧义连接兼容登记；跨空间歧义不自动授权。仓库映射唯一，远端扫描再次核对 repository ID。

用户查看可连接仓库、连接列表、初始导入与后续对账结果，显式停用/恢复、请求只读对账。一个扫描 operation 对应多个分页 WorkJob 及资源观察义务；页面展示业务数量/失败原因，不列出全部内部 Job。源代码/PR/CI 的权限范围仍以部署 App 配置为准。

GitHub Task 的标题、描述与 open/closed 状态走 intent；202 表示受理，confirmed 之前不解除依赖。completed→DONE；not_planned→CANCELED；reopen→TODO。负责人、优先级、日期、依赖由本地管理。外部 confirmed 是独立映射，不走人工 TRIAGE 状态机。PR/commit/CI 仅作证据，不自动完成任务。

UNKNOWN/SEND_STARTED 只能 GET 观察确认，不提供重新 PATCH 按钮。停用连接、撤权或归档不会假装撤销已经发出的请求。GitHub 与本地没有跨系统原子性；GET/PATCH 间的未观察并发仍是已知边界。

## 整体交互审查与本轮取舍（2026-09-27）

先以真实 Chromium 浏览已有团队、项目、任务、成员、文档、CSV、GitHub 和390px页面，再按共因修正：

| 优先级 / 共因 | 实际问题 | 本轮处理 |
|---|---|---|
| 高 / 结果含义 | 预检查和已提交行混用状态；异步请求统一显示“已保存”；所有409都建议刷新 | 分开预检查、受理、处理中、部分成功和确认；冲突保留输入，可另页对照；成环/最后角色/归档分别解释 |
| 高 / 权限与生命周期 | 归档后仍显示任务/文档/导入写表单；普通成员看到分诊接纳；成员管理默认可能误降自己角色 | 归档只读、按角色显示接纳；成员必须明确选择，读取其当前角色；危险操作说明影响并确认 |
| 中 / 信息与词汇 | 英文枚举、文档UUID、双订阅按钮；任务详情长且评论编辑器全展开 | 共用中文词汇；关联标题、实际订阅状态、紧凑属性和内容跳转；评论按需展开编辑 |
| 中 / 连贯反馈 | 创建/验证后提示被路由清掉；任务列表返回丢失筛选；导入需要手动反复刷新 | 跳转保留结果与下一步；项目筛选留在URL；导入处理中每2秒查询真实行结果 |

早期体验修正仅调整只读聚合与入口展示。后续任务详情修正已按上文收紧任务编辑权限，并在服务端执行；GitHub intent 同样要求任务编辑权限，连接管理仍需要维护者。任务状态机、导入身份及 GitHub 发送协议保持原合同。

参考于本轮访问的官方资料：[Linear 依赖关系](https://linear.app/docs/issue-relations)明确区分 blocked by / blocks，本产品用“上游依赖 / 下游工作”说明方向，保留自身 DONE 判断规则；[GitHub 筛选与搜索](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests)提供负责人和状态过滤，本产品用现有服务端筛选与可返回的 URL；[Linear 通知](https://linear.app/docs/notifications)作为个人通知入口参考。只借鉴这些局部模式，不声称实现完整 Linear/GitHub 行为。

低优先级保留：详情评论/活动各50项、文档和依赖候选有界；超大列表、复杂看板、富文本和全站草稿管理不在本轮。版本冲突时当前表单保留输入，刷新前仍需复制草稿或在新标签页对照，不自动合并正文。权限回归见 [TaskPermissionsIT](../src/test/java/dev/workhub/phase3x/TaskPermissionsIT.java)。


## 多成员共用生成模型额度

开启共享模型治理时，成员QA和后台分诊竞争供应商账号/模型类别对应的请求额度；项目不是各自独立拥有一份供应商额度。费用授权仍独立绑定计费合同与币种，由MySQL预留与结算，不新增Workspace钱包或自动续费。新scope须经运维确认限额与恢复期后初始化；Redis丢状态或故障时停止未确认的出站调用。

短时拥堵可以有界等待；费用不足、等待超时、供应商429、熔断或准入基础设施故障会留下明确失败原因，用户可继续手工处理任务。系统不把依赖故障伪装成无证据回答，也不在后台无限重试。已经发出的请求仍结算或记UNKNOWN；关闭自动分诊或撤权会阻止下一次发送。第一版不保证不同Workspace排队公平，也不支持等待时释放worker后无损恢复模型上下文。


## 后台分析进度与恢复（2026-10-16）

QA及分诊的进度是后台已持久化阶段的快照，不是完成百分比或模型思维过程。名额等待、供应商冷却、预算不足、依赖暂不可用和证据不足分别说明；等待期间无需重复提交。终态答案仍检查当前来源是否有效，分析完成不等于提案已批准。

同一页只关注一个Run；链接保留项目/任务及Run上下文，刷新和断线只恢复读取。提交结果不确定时保留原问题及请求键，重试确认原意图；明确的新分析才使用新键。QA仅发起人可读，分诊需当前维护者；长连接每次发送重新检查会话及成员权限，撤权检查后不再发送内容，已在途或已显示的内容无法召回。慢连接采用快照合并，不保证所有瞬时阶段都展示。
